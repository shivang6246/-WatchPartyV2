# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

WatchParty: synced watch parties in any browser (phones included) for YouTube, direct MP4/WebM/HLS and Vimeo. One Spring Boot backend serves both the Next.js web client in `frontend/` and a separate Chrome extension (not in this repo) that handles DRM platforms on desktop. `README.md` is the design doc — read it before changing sync, auth or data-model behavior.

- `backend/` — Spring Boot 3.5, Java 21, Maven (no wrapper; use a local `mvn`). Supabase (Postgres, via JPA/Hibernate + Flyway) for durable data, Redis for hot state.
- `frontend/` — Next.js 16, React 19, Tailwind 4, `@stomp/stompjs`. **Read `frontend/AGENTS.md`**: this Next.js version has breaking changes; consult `frontend/node_modules/next/dist/docs/` before writing Next code. That file is regenerated by `next dev`.
- `ops/` — `Caddyfile` (TLS proxy, `proxy` profile), `prometheus/` and `grafana/` (the `observability` profile; the dashboard JSON is in `ops/grafana/dashboards/`).

## Commands

Full stack (needs `.env` from `.env.example`: `DATABASE_URL`/`DATABASE_USER`/`DATABASE_PASSWORD`, `REDIS_PASSWORD`, `JWT_SECRET`; `YOUTUBE_API_KEY` optional):

```bash
docker compose up -d --build                       # Supabase via DATABASE_URL
docker compose --profile local-db up -d --build    # bundled postgres:16 instead
SITE_ADDRESS=your.domain docker compose --profile proxy up -d   # Caddy/TLS
docker compose --profile observability up -d       # Prometheus + Grafana on :3001 (needs GRAFANA_PASSWORD)
```

Web on http://localhost:3000, API + Swagger at http://localhost:8080/swagger-ui.html. Postgres and Redis publish no ports.

Running the backend outside Docker (IDE or `mvn spring-boot:run`) reads `backend/.env.local` (gitignored; template in `backend/.env.local.example`) via `spring.config.import`, and needs a reachable Redis (`REDIS_HOST`, `REDIS_PASSWORD`). It deliberately does *not* read the root `.env`: that sets `REDIS_PASSWORD` for the compose Redis, which would break a passwordless local Redis. There are no defaults for the database or `JWT_SECRET`: both blank means startup fails, by design.

### Where secrets live
Two gitignored files, by who reads them, plus the host's secret store in production. A value used in both places has to be set in both.

| | reader | holds |
| --- | --- | --- |
| `backend/.env.local` | Spring, for a run outside Docker | `DATABASE_*`, `JWT_SECRET`, `REDIS_PASSWORD`, `YOUTUBE_API_KEY`, `GOOGLE_CLIENT_*`, `SMTP_*`/`MAIL_FROM`/`WEB_BASE_URL` |
| root `.env` | Docker Compose only | the same, plus `POSTGRES_PASSWORD`, `GRAFANA_PASSWORD`, `SITE_ADDRESS`, `NEXT_PUBLIC_*` |
| host secret store | production | everything above; never deploy a `.env` file |

- **Never put a literal secret in `application.properties`** (it is committed): always `${VAR}` or `${VAR:}`. Same for `docker-compose.yml`, Dockerfiles, source and tests.
- **`NEXT_PUBLIC_*` is public** — it is compiled into the bundle every visitor downloads, so it holds only the API/WS URLs and feature flags. This is why the YouTube key is proxied server-side (see Catalog).
- `.gitignore` covers `.env` and `.env.local` at any depth; the `*.example` templates are committed and must stay free of real values.
- Production uses its own `JWT_SECRET` and database, never the local ones. Rotating `JWT_SECRET` signs everyone out (tokens carry a `kid` header, so a rotation can be staged).

## Architecture

### Two stores, strict split
Postgres on Supabase (nine tables: `app_user`, `refresh_token`, `email_verification`, `pending_registration`, `room`, `room_member`, `chat_message`, `playback_event`, `friendship`) is durable truth. Redis holds live playback state, presence, watchdog deadlines, cross-instance fan-out, rate-limit counters and the YouTube search cache. `sync/StateSnapshotJob` writes Redis state back to Postgres every 30 s, updates the active-room gauge, asks the watchdog to audit each room and expires rooms. `sync/RetentionJob` purges chat/playback history 30 days after close and deletes expired refresh tokens, verification links and finished/abandoned sign-ups (Postgres has no TTL index).

- **Connections are scarce.** The app reaches Supabase through its session pooler, which allows 15 clients per project on the free tier, counting idle ones. Hikari holds one idle connection (`minimum-idle=1`, `idle-timeout` 60 s) and grows to `DATABASE_POOL_SIZE` (5) under load, so a restart overlapping the old process or a second instance still fits. A start that fails with `EMAXCONNSESSION` (or "This connection has been closed") means the pooler is full, not that the code is broken.
- **Schema changes are new Flyway files** in `backend/src/main/resources/db/migration` (`V2__...sql` and so on). Never edit an applied migration: Flyway checksums it and refuses to start. Hibernate runs `ddl-auto=validate`, so an entity that drifts from the SQL fails at boot. Tables live in the `watchparty` schema, not `public` (Supabase exposes `public` via its REST API with the anon key). Every table has RLS enabled with no policies, so new tables need `alter table ... enable row level security` too. Don't `ALTER` `flyway_schema_history` inside a migration: Flyway holds a lock on it and the migration deadlocks.
- **Every write to an existing room goes through `RoomService.mutate`** (or `tx.execute` with `rooms.findByIdForUpdate`): a short transaction that takes the row lock (`SELECT ... FOR UPDATE`), applies the change to the fresh copy, and commits. Host edits, queue advances from any member and the snapshot sweep all write that row; the lock serialises them so none undoes another. Don't `rooms.save()` a room loaded earlier in the request; `save` of a new room is only in `create`. `@Transactional` on a method called from the same class does nothing (proxy), which is why `RoomService` uses a `TransactionTemplate`.
- Entities extend `common/AssignedIdEntity`: the UUID is assigned at construction (ids are needed before save), and `Persistable.isNew` makes the first save a plain INSERT. That's also what lets the `(room_id, user_id)` unique constraint catch two racing joins (`join` catches `DataIntegrityViolationException` and returns the winner's row).
- `spring.jpa.open-in-view=false`: nothing lazy-loads outside a transaction, and there are no JPA associations; rows reference each other by id columns.
- No joins needed for display: denormalize display data (author name on chat messages and queue items, video title/thumbnail on the room).

### Realtime path
STOMP over `/ws` (`config/WebSocketConfig`). Client sends to `/app/room/{roomId}/{playback|chat|reaction|typing|heartbeat|resync}` and `/app/session/time`; server broadcasts on `/topic/room/{roomId}/{playback|chat|members|activity}` and per-user `/user/queue/{errors,time}`. Handlers live in `sync/RealtimeController`.

- `chat` carries only stored `ChatMessageView`s: the Chrome extension renders that topic, so don't put other event shapes on it. Ephemeral events (reactions, typing) go on `activity`.
- `members` carries typed events (`roster`, `health`, `left`, `room`, `closed`, `host`, `host-away`, `host-back`, `host-lost`, `queue`); `MemberEvent` in `frontend/src/lib/types.ts` mirrors them.
- **Presence is live, and the Redis presence set is its only source.** `RoomStateService.heartbeat` returns true when a member *becomes* present, and that transition broadcasts the roster: on STOMP CONNECT (`StompAuthInterceptor`) and on a heartbeat after a gap (`RealtimeController.heartbeat`, which also heals a "left" sent when one of two tabs closed). A disconnect publishes `left`, unless the same member still has another open session on this instance (`SessionRegistry.hasOtherSession`: one of two tabs closed); a second tab on another instance heals with its next heartbeat. Members who time out without a disconnect (heartbeats every 5 s, `app.room.member-heartbeat-ttl` 12 s) are pruned by `RoomWatchdog.sweepPresence` every 2 s (`app.room.presence-sweep-ms`), which walks only the rooms in the Redis set `wp:presence:rooms` (added to on every heartbeat, dropped once a room's presence set is empty) and publishes `left` for each; the snapshot sweep's `audit` still runs `expirePresence` too. `expirePresence` claims stale members in one Lua script, so with several instances each departure is announced once. `presentMembers` filters by score and never prunes, so nothing else can swallow a departure. The client never marks itself absent (`withSelfPresent` in `useRoom`; a `left` about yourself is another tab of yours). Outside a room the counts are live presence too: `RoomCard.memberCount` (home and Rooms) and `RoomPreview.memberCount` (the join screen) are `presentMembers(...).size()`, never the database's "joined and not left", and `MyRooms` re-fetches every 5 s while visible and on focus (`roomsFor` is two queries whatever the number of rooms). The client diffs rosters in `useRoom` into `presence` (joined/left) lines in the chat timeline. A leave followed by a rejoin within 15 s (a reload) shows nothing. The roster also lists members who never left over REST (closed the tab) with `present: false`; the People tab (`MembersPanel`), the counts and `SyncStatus` show only `present` members, so they are live, never "everyone who once joined".
- Sending a SEND/SUBSCRIBE to another room's destination is fatal to the session by design (interceptor throws → ERROR frame).

All broadcasts go through `sync/RoomEventPublisher`, never `SimpMessagingTemplate` directly. It publishes an `Envelope` to the single Redis channel `wp:room-events`; `RoomEventSubscriber` on every instance (including the sender) calls `deliverLocally`. Three modes: `publish` (room topic), `sendToMember` (a member's `/user/queue/errors` on whatever instance holds them) and `disconnectMember` (same, then closes their sockets). `sendError` is local-instance only, so use it only for replying to the frame being handled. Member notices carry `roomId`, because a user destination reaches that account's tabs in other rooms too, and the client filters on it.

`security/SessionRegistry` maps raw WebSocket sessions to member ids (registered by a handler decorator in `WebSocketConfig`, bound at CONNECT in `StompAuthInterceptor`). That's what lets a kick actually close a socket, with close code 4001 (`SessionRegistry.REMOVED`), which the client treats as "don't reconnect".

### Room watchdog (`sync/RoomWatchdog`)
There are two Redis sorted sets of deadlines, `wp:watch:host-away` and `wp:watch:room-empty`, scored by due time. A 5 s sweep claims due entries with `ZREM`, so exactly one instance acts on each. Every deadline is re-checked against live presence when it falls due.
- Signals come from: STOMP CONNECT (`onMemberConnected`: marks presence, cancels both), `SessionLifecycleListener` on disconnect and REST leave (`onMemberGone`), and `audit()` from the snapshot sweep, which catches members who aged out without a disconnect.
- Host away: `app.room.host-grace` (45 s), then `pickSuccessor` picks the earliest-joined, present, registered, non-removed member → `RoomService.transferHost(..., "failover")`. With only guests left, the room is unlocked and gets a `host-lost` event.
- Empty: `app.room.empty-grace` (10 m), then `RoomService.closeRoom(room, "empty")`. All closes (host / empty / expired) go through `closeRoom`.

### Sync engine (server `sync/`, client `frontend/src/lib/{clock,sync,player}.ts`)
- Room state is a position anchored to a server timestamp plus speed; clients compute `position + (now - anchor) * speed` against their own corrected clock. Never broadcast a live position.
- `RoomStateService` applies each event in a Redis Lua script that writes state and assigns a monotonic per-room sequence atomically. Clients drop any event whose sequence isn't greater than the last applied. Keep ordering inside that script.
- A new video (host change or queue advance) goes through `RoomStateService.resetPlayback`, which continues the sequence from `max(live, snapshot) + 1`. Don't use `clear` + `hydrate` for this: `hydrate` seeds the sequence from the up-to-30 s-old snapshot, and clients would drop the reset.
- **Playback is host-only**: `Room.locked` is always `true` while the room has a host, so `PlaybackService` refuses play/pause/seek from anyone else (`room_locked`, with the authoritative state sent back). Hosts cannot unlock it: `PATCH {locked:false}` is 403 `host_only_playback`, and `HostMenu` has no such option. The one exception is the watchdog: a room whose host is lost with only guests left is unlocked so it can't freeze, and `RoomWatchdog.onMemberConnected` re-locks it the moment a host connects (which also re-locks rooms unlocked before this rule). Queue advance on `ended` is a REST call and ignores the lock.
- Client positions are never authoritative: seeks are requests, validated against media duration and re-stamped with the server clock. Heartbeat positions are telemetry only (they drive the host's "N members behind" and the drift histogram).
- **An event is anchored when the member pressed, not when the frame arrived.** An intent may carry `serverTs` (the press time on the client's synced clock; omitted until the clock has synced), and `RoomState.anchorFor` accepts it within bounds: never in the future, never more than `MAX_BACKDATE_MS` (1.5 s) back, never before the current state's own anchor. Play/pause take the room's projection *at that moment*. This is what lets the presser's player move at the click and still agree with the echo (otherwise the echo finds it ahead by the trip and seeks it, which on YouTube means a re-buffer right after pressing play). Guests start slightly further in to match.
- **Keep the database off the playback path.** `PlaybackService.handle` reads Redis first and loads the room row only for a cold room; the one DB read before the broadcast is the caller's membership check, and the `playback_event` history row is written *after* publishing (a failure there is logged, not returned). Each Supabase round trip here is felt on every press.
- In a paused room always `pause()` *before* `seek()`, and `SyncEngine.tick` re-pauses any player whose `isPlaying()` is true. YouTube's `seekTo` resumes a player that isn't already paused; seek-then-pause leaves the video running while the engine keeps seeking it back (it plays in stutters instead of freezing).
- The reverse holds too: `tick` calls `play()` on a player that stopped while the room plays (a click on the YouTube iframe, an autoplay block, a backgrounded tab). It doesn't do this in the last 1.5 s, where a stopped player has simply finished and `play()` would restart it from 0. After 3 stalled ticks `diagnostics.blocked` is set, and `PlayerSurface` shows a "tap to join in" button that calls `SyncEngine.userStart()` inside the click (only a user gesture clears an autoplay block).
- A seek intent carries the room's *current* `playing` (`playingRef`), never `true`, so scrubbing never starts or stops the room.
- **Every room plays in WatchParty's own player** (`PlayerSurface`): the video is chromeless and all controls are drawn over it, video-site style, for YouTube and direct links alike (Vimeo keeps its own iframe controls; DRM rooms are chat-only). A seek bar with the loaded fraction and a hover time, play/pause, ±10 s (buttons hidden on a phone, double-tap a side instead), volume (slider on hover, from `@xl`), time, the room's speed badge, captions (CC), a settings panel (speed for everyone, host only; quality where the player has a ladder; caption language), picture-in-picture (video element only) and fullscreen. They hide 2.6 s after the last move while playing and stay up while paused, at the end, over the bar or with the panel open. A click on the picture toggles the room, a double-click is fullscreen (the single click waits 220 ms to tell them apart); on a phone a tap shows/hides the controls and a double tap on the left/right third skips. **Presses are handled on `click`, never on pointer-up**: a finger's late click lands on whatever is under it by then, and controls revealed on pointer-up took it (a tap pressed the big pause button it had just shown). Keys: Space/K, J/L and ←/→ (±10 s), ↑/↓ volume, M, C captions, F, Escape closes the panel; a focused control button keeps them working (only Space/Enter are its own). Play, pause, seek and speed are the room's (`useRoom`'s `intent`/`setSpeed`, host-only; anyone else gets `explainLocked`'s hint), volume/captions/quality/fullscreen the viewer's. "Watch again" at the end is `restart()`: one seek that carries `playing`, never a seek then a play (two frames can be handled in either order).
- **YouTube is a picture only** (`YouTubePlayer`): `controls: 0`, `disablekb`, `fs: 0`, the iframe `pointer-events: none`, and sized as the fitted 16:9 picture plus 30% above and below, centred and clipped, so YouTube's title bar (pinned to the player's top) and paused "More videos" panel and logo (pinned to its bottom) fall outside the frame. YouTube centres the picture, so those bands are always equal, and its captions sit in the bottom one: with captions on the iframe is the picture alone (the title bar can then show at start and while paused), resized only when captions are switched. Captions use the IFrame API's undeclared `loadModule`/`setOption("captions", ...)`; the track list arrives through `onApiChange`, and the wanted track is set again on every change because a track set while the module loads can be dropped. Our opaque big play button covers YouTube's red one before the first play, and our end card covers its end screen. It loads from `youtube-nocookie.com` (as the home trailer does). When YouTube refuses a video (`onError`: 100 removed, 101/150 embedding not allowed, 152/153 page not accepted), the player is detached (else the engine keeps correcting it and asks for a resync every tick) and the stage shows a "YouTube won't play this here" card with the reason, "Watch on YouTube" and, for the host with a queue, "Skip to next", instead of our controls over YouTube's error screen. Some label-owned videos (music) return 150 on a page reached by a bare IP address, though they play on `localhost` and real domains, so test phones over a LAN with other videos (trailers play there). There is no reading of YouTube's own controls any more (the old `ViewerAction` path is gone): no one can reach them.
- **Direct video links (`hosted`)**: a bare `<video>` under the same controls. For whoever may control the room, presses and keys go through `intent`, which moves this player at once (`SyncEngine.applyLocal`, then a hold until the echo) and flips `playing`; only a sent frame does this, so a dead socket changes nothing. The scrub bar commits on pointer-up, touch-end, key-up and blur, and holds the target for 1.5 s so it doesn't snap back during the round trip. The duration is polled every tick until the player reports one, because YouTube often has none at `onReady`.
- **Speed is the room's**: the host's `rate` event carries `speed`; `hardApply` sets the player's rate to `state.speed` on every event (it used to be restored only after a drift nudge, so a speed change reached nobody).
- `SyncStatus` (under the player) is the room's live readout: a ring for this screen's measured drift, "All N in sync" / "N of M in sync" from present members and the server's `health` events, and who holds the remote.
- Clock sync: 5 probes on connect and every 30 s, offset from the lowest-RTT probe.
- **Local-only player controls** (never sent to the room) live on `PlayerHandle`: `setVolume`, `setMuted`, `getQualities`/`setQuality`, and the optional `getBufferedFraction`, `getRates`, `getCaptionTracks`/`getCaptionTrack`/`setCaptionTrack` ("auto" picks the viewer's language, then English), `togglePictureInPicture` and `requestNativeFullscreen`; `PlayerSurface` polls the handle every 250 ms and shows a control only when the player offers it (quality only with more than one entry, CC on YouTube or when an HLS stream lists subtitles). `.m3u8` goes through **hls.js whenever `Hls.isSupported()`** (imported on demand, so other rooms never download it), native only as the fallback (iOS Safari): Chrome answers `"maybe"` to `canPlayType` for HLS and then plays it with no quality ladder. YouTube returns no qualities on purpose (its quality API is deprecated and ignored). `HostedPlayer` re-announces its handle when the ladder arrives, which is what makes the menu appear.
- **Fullscreen**: F, the button or a double-click takes the whole `.stage` section (screen with its controls, hint and reactions), not the bare player; the layout is in `.stage:fullscreen` in `globals.css`. iOS only allows fullscreen on the `<video>` itself (`requestNativeFullscreen`), so an iPhone gets no fullscreen button in a YouTube room.
- Drift ladder: <250 ms nothing; 250 ms–2 s rate 0.97/1.03; >2 s hard seek; >30 s resync (the client also sends `/resync`). YouTube can't do fine rates (`PlayerHandle.fineRateSupported = false`), so it uses 0.75/1.25 up to 2.5 s and only seeks beyond that, since a YouTube seek costs seconds of buffering. `SyncEngine.drainCorrections()` counts each tier, and those counts ride on the next heartbeat for metrics.
- **A seek on a playing room aims ahead** (`SyncEngine.seekPlaying`): at the projection plus a lead, because the room keeps moving while the player loads. Seeking to "now" lands the player behind by its load time, which triggers another seek, forever (endless buffering at a steady few seconds of drift). The lead starts at 900 ms for YouTube and 150 ms for a video element, and is learned from where each seek lands (damped, capped at 6 s). `hardApply` only plays or pauses a player that is already within `ignoreMs`, so play/pause events and resyncs don't seek in-sync players.
- The ladder holds off when its measurement can't be trusted, because on YouTube every seek re-buffers. **While the player is buffering** (`SyncEngine.setBuffering`, fed from `useRoom.setBuffering`) nothing corrects for up to 8 s: seeking a player that is refilling throws the buffer away and turns one stall into a loop. After it refills there is a 700 ms settle. **A tick more than 1.8 s after the previous one** (the page's thread was blocked) is skipped, since the player's reported position is stale then.
- Never resize the player as a side effect of UI: YouTube switches quality on a resize and re-buffers. That is why the viewport has no `interactiveWidget: "resizes-content"` (the keyboard would reflow the room) and why the landscape player is sized in `svh`. Keep chat rendering cheap too (`ChatPanel`'s list is memoised, timestamps use one shared `Intl.DateTimeFormat`): on Android the YouTube iframe often shares the page's main thread.

### Queue
`Room.queue` is a `jsonb` column holding only *upcoming* `QueueItem`s. They're serialized field by field (`@JsonAutoDetect`), and equality is by `itemId` so Hibernate can tell an unchanged queue. The current video stays in the room's `video*` fields, identified by `currentItemId`. Always assign a *new* list (`setQueue`), never mutate in place. Every queue write happens under the row lock. Reorder must name every current item exactly once, else 409 `queue_changed`. An advance checks `currentItemId` under the lock, which makes N members all reporting "ended" at once advance the queue only once. Any member may report `ended`, but the server only accepts it if its own projection is within 5 s of its own known duration (the reporter's duration is never trusted). `skip` and all edits are host-only via `requireQueueControl`. Max length is `app.room.max-queue`.

### Auth model (`auth/`, `security/`)
A token proves identity only; every room operation loads the caller's `room_member` row and checks its `MemberRole`. Credentials: access JWT (15 min, memory), rotating refresh token with reuse detection (HttpOnly cookie `wp_refresh`, hashed at rest, TTL index), guest token (one room, ≤24 h), and a WebSocket ticket (30 s, single use, from `POST /api/v1/ws-ticket`, sent as the STOMP `ticket` connect header and checked by `StompAuthInterceptor`) — never put the JWT in the WS URL. The room code alone is enough to join: `GET /rooms/{code}/preview` is public, and `POST /auth/guest` takes `roomCode` *or* `inviteToken`, then `join` needs no invite. The invite link still works. Code guessing is slowed by the per-IP `ROOM_LOOKUP` (preview) and `GUEST_ISSUE` limits; a guest pass stays scoped to its one room. Hosts must be registered users; only the host's `RoomView` carries `inviteToken` (the client refetches after becoming host). A guest who registers mid-room has their member row rebound, not duplicated. Removed members are refused at ticket, join, CONNECT and every frame; muted members can't chat, react or send typing, and the host can't be muted or removed.

**Email verification (`auth/EmailVerification*`, `auth/Mailer`, `auth/MailConfig`):** one email carries a six-digit code *and* a link, both on the same row (256-bit token and the code, each SHA-256 hashed at rest, `app.verification.ttl` 24 h). They gate exactly one thing — `RoomService.create`. Guests never need an account, so an unverified user can still join, watch, chat and react; only hosting is refused (403 `email_unverified`). Issuing deletes the account's earlier unused rows, so an old email stops working. Google accounts are verified on creation.
- `POST /auth/verify` (link) is public: the token is the proof, and mail is often opened on a device that is not signed in. `POST /auth/verify/code` and `/auth/verify/resend` need the session, because six digits is only meaningful against one account.
- The code row counts wrong tries and dies after `MAX_CODE_ATTEMPTS` (6); that, not the hash, is what makes guessing pointless. The message says how many are left, then tells them to ask for a new code.
- **Where verification is enforced, `register` creates no account.** The sign-up (password already hashed, plus any guest pass so the seat is kept) waits in `pending_registration` and `register` answers 202 `{pending, email}` with no session. `POST /auth/register/confirm` takes `{email, code}` or `{token}`, creates the account already verified and signs it in; `/auth/register/resend {email}` re-sends. Registering the same address again replaces the waiting row. The client goes `/register` → `/verify?email=…` (code form); the email's link is `/verify?signup=…`. With verification not enforced, `register` signs in straight away as before (the smoke run relies on this).
- The older per-account path (`/auth/verify`, `/verify/code`, `/verify/resend`, link `/verify?token=`) remains for accounts created unverified before this, or on a stack that doesn't enforce verification.
- **Enforcement follows the mail setup**: `EmailVerificationService.required()` is true when `spring.mail.host` is non-blank, and `app.verification.required` overrides either way. With no SMTP the mail is logged instead, so a dev machine (and the smoke run) can host freely. Pick the `Mailer` on a *non-blank* host, not on the property merely being set: `${SMTP_HOST:}` leaves an empty string behind.
- `management.health.mail.enabled=false` — otherwise the health endpoint dials SMTP and reports the whole app down when no host is set.

**Client token handling:**
- `useRoom`'s `tokenRef` holds only a *guest pass*. Signed-in users pass no token, so `apiFetch` sends the current in-memory access token and refreshes it on a 401.
- Never pin an access token in a ref or closure: it expires after 15 min, and `apiFetch` skips the refresh whenever a token is passed explicitly.
- **The page-load session restore is `restoreSession()`** (started once, shared): the auth provider and any early API call both use it, and `apiFetch` waits for it when it has no token yet. Without that, a component whose effect runs before the provider's (children's effects run first) sent its request with no token and logged a 401 before the retry. The restore calls `POST /auth/refresh?optional=true`, which answers 204 when there is no refresh cookie at all ("no session" is not a failure); an expired or revoked cookie, or a call without the flag, is still a 401.
- `RoomConnection.beforeConnect` must never throw (stompjs would surface it as an uncaught error). Ticket failures with 401/403 call `onAuthFailed`, which clears a dead guest pass and re-enters the room; other failures retry after 3 s. A 401/403 from `join` also falls back to the name screen. To test expiry quickly, start the backend with `--app.jwt.access-ttl=15s`.

### Friends (`friend/`)
Accounts only (a guest gets 403 `account_required`). `friendship` holds one row per pair, `pending` (a request; `requested_by` asked) or `accepted`. The pair is stored ordered (`user_low < user_high`) so either side's request hits the same unique key: adding someone who already asked you accepts, and two people adding each other at once become friends rather than two requests (the loser of the insert race re-reads and applies the same rule). **Order pairs with `FriendService.pair`** (canonical-text order, which is Postgres's uuid order); `UUID.compareTo` compares signed halves and disagrees for some pairs, which would break the table's check constraint.
- Ways to add, all `POST /friends/requests` (rate-limited `FRIEND_REQUEST`, per account): by email (a clear 404 for an unknown address: register already says whether an email is taken), by someone in your room (`roomId` + `memberId`; you must be a member, they must have an account), or by a friend-link `code` (`app_user.friend_code`, made on first `GET /friends/link`, rotated by `POST /friends/link/rotate`). A link is its owner's standing consent, so it makes an accepted friendship straight away. The web link is `/friends?add=CODE`.
- "Watching" is live presence, never history: `FriendService.watching` loads open-room memberships of friends in one query (`RoomMemberRepository.findOpenByUserIds`) and keeps those with a heartbeat within the TTL (`RoomStateService.lastHeartbeat`), the most recent room per friend. Only for friends with `app_user.share_activity` on (default); off, they stay on your list without a room.
- `GET /friends/activity` (watching friends, incoming count, friend count) is what the client polls: `lib/friends.ts` runs one 8 s poll shared by the home row (`FriendsWatching`) and the Friends tab's badge. `GET /friends/rooms/{roomId}` maps members of a room to `friend`/`outgoing`/`incoming` for the People tab's "Friend"/"Accept"/"Requested".

### Catalog (`catalog/`)
youtube.com cannot be iframed, so "YouTube in the app" means the backend proxies the Data API (`/api/v1/catalog/youtube/{search,trending,trailers}`, cached in Redis ~10 min because searches cost 100 quota units) and the client renders the results, embedding only the IFrame player. The API key stays server-side. With no key, `/catalog/sources` reports `browsable: false` and `/catalog/resolve` uses keyless oEmbed; that must keep working.
- `trailers` feeds the home screen's backdrop: a search for "official trailer", embeddable, most-viewed first, published in the last 30 days, then `pickTrailers` drops Shorts, clips under 45 s and live streams. (The Film & Animation popular chart costs 1 unit instead of 100 but is Shorts and memes, not trailers.) It is the one **public** YouTube endpoint (`SecurityConfig`), which is affordable only because it takes no parameters and is a single cache key held for 6 h (~400 units a day, whoever asks). `/catalog/sources` is public too (server configuration, no quota), so public pages can read it; trending and search are not, so the client only calls them for a signed-in user (`TrendingRow`, Discover), never to be refused. Keep it that way if you touch it; never make `search` public. `trending` maps any region that isn't an ISO country code to `US` (`normalizeRegion`), so callers can't mint cache keys there either.

### Observability
Every meter is defined in `metrics/WatchPartyMetrics` (keep tag values bounded; never tag with ids or user input). Exposed at `/actuator/prometheus`, which is `permitAll` in `SecurityConfig` and kept private by Caddy (`/actuator/*` → 404) and the loopback-only port. Prometheus names: `watchparty_rooms_active`, `watchparty_ws_sessions`, `watchparty_redis_apply_seconds`, `watchparty_sync_drift_milliseconds`, `watchparty_sync_corrections_total{tier}`, `watchparty_playback_events_total{action,result}`, plus counters for chat, reactions, failovers, closes, kicks and queue advances. If you rename a meter, update `ops/grafana/dashboards/watchparty-overview.json`. In Docker, logs are ECS JSON (`LOGGING_STRUCTURED_FORMAT_CONSOLE`, set via `LOG_FORMAT`); use SLF4J `addKeyValue` for fields you want queryable (see `PlaybackService.recordCorrections`).

### Design system (frontend)
Quiet, premium and mobile-first: a warm near-black, off-white type, one restrained champagne accent used sparingly, hairline borders and soft dark shadows for depth (no coloured glows), and concentric hairline rings as the only ornament. Build for a 390px phone first and widen from there.
- **Tokens:** all colours live in `@theme` in `src/app/globals.css` (`ink`, `stage`, `panel`/`panel-2`/`panel-3`, `line`/`line-strong`, `cream` (the off-white type colour), `muted`, `faint`, `gold`/`gold-bright` (hover)/`gold-soft` (accent text)/`gold-deep`, `own` (your own chat bubble), `ember` for danger, `sage` for ok). Use those utilities, never raw Tailwind palettes (`zinc-*`, `rose-*`…). The accent is for small things (live dots, the sync ring, labels, the "Next" tag, an unread count); primary actions are `bg-cream text-ink`, never a gold fill. Text on `bg-gold` is `text-ink` (white fails contrast).
- **Fonts:** self-hosted with `next/font/google` in `layout.tsx`: Plus Jakarta Sans → `font-sans` for the interface (weights 400–600; nothing heavier); JetBrains Mono 400/500 → `font-mono` for codes and timecodes (not preloaded); Newsreader **400 only**, roman and italic → `font-serif` for display type (a single static weight is half the bytes of the variable range, so don't add a serif weight without need): page titles, the greeting, the wordmark, empty states, and an italic word via `Accent`. Room and video titles stay in the sans.
- **CSS helpers:** `.spotlight` (a faint warm light from the top, per page), `.halo` (a hairline ring; absolutely positioned, size it with a width; `.halo-dim` for a fainter outer one; nest two for the ring motif), `.panel`, `.ticket` (mono room code on a hairline), `.thin-scrollbar`, `.no-scrollbar`. Over the home trailer: `.glass` ("Now showing" and the phone's Start/Join card: blended into the trailer with no edge of any kind, so no border, inset highlight or drop shadow, all of which draw the outline; the tint and gloss sit on `::before`, feathered out toward every side with a mask; it sets `position: relative` and `isolation: isolate`), `.glass-inset` (a recessed field inside it: the code field via `JoinCodeForm glass`), `.glass-raised` (the selected tab, which has no track behind it, the trailer's round buttons, the waiting Join button) and `.over-picture` (a text shadow). The gloss is drawn, never `backdrop-filter`: a blur over a playing video is recomputed every frame. They sit in `@layer components`, so utilities such as `focus-within:border-*` still win. `body` has `overflow-x: clip`; don't switch it to `hidden` (it would break the sticky side panel).
- **Mobile rules:** inputs are 16px below `sm` (`text-base sm:text-sm`), or iOS zooms on focus. Tap targets are at least 44px. Use `dvh`, not `vh`, for full-height layouts. No `backdrop-blur`, blend modes or animated filters on anything big (they are what makes a phone stutter). `land:` (a custom variant: landscape, under 560px tall, under `lg`) is a phone on its side. A `grid` that only gets columns at `lg` needs `grid-cols-1` below it: the implicit `auto` column grows to the widest unbreakable line (a URL, a mono code), which pushed the Friends page 80px past a phone's edge. Size things for three bands: phone (the base, compact: page titles 28px, cards `p-[18px]`), tablet (`sm`/`md`: the home cards go two-up at `md`) and `lg` (the desktop layout). Draw an icon button smaller if it looks heavy, but keep its 44px hit box (see `HomeGreeting`).
- **Navigation:** Home `/`, Discover `/discover`, Friends `/friends` (badge: requests waiting on you), Rooms `/rooms`, Account `/account`. `components/AppNav.tsx` exports `AppNav` (the floating tab bar below `lg`: edge to edge on a phone, a centred pill capped at `26rem` on a tablet, icons only under `land:`; pages that show it keep `pb-32` so it never covers their last row) and `AppHeader` (the wide-screen top bar with the same links and the account menu, `lg` up). Below `lg` each page opens with its own serif title instead. The room and the sign-in pages have neither.
- **Home backdrop** (`components/home/Hero.tsx`): a random trailer from `trailers` plays muted, full width behind the hero, on youtube-nocookie, with a "Now showing" card (Watch together, next, sound). It plays at every width (muted + `playsinline` is what lets a phone autoplay it); reduced motion or Save-Data starts on the still, and the play control makes the player on demand. **It is our own player around a chromeless embed**: YouTube's iframe is only the picture (`controls: 0`, never clickable) and every control is ours (play/pause, sound, next, progress hairline in "Now showing"). A YouTube video can't be played outside YouTube's embed (no stream URLs; extracting them breaks its terms and the URLs are bound to the fetching IP), so "custom player" means this. `showing` follows the real state: `PLAYING` sets it, `PAUSED`/`CUED`/unstarted clear it (buffering changes nothing), and the still covers the embed whenever it is not playing, so YouTube's own paused screen, title bar and "More videos" never show; it fades in ~5 s after each start (`Hero.revealed`, `YOUTUBE_CHROME_MS`), because YouTube draws its title bar over the start of playback, and the phone embed its centre pause button (gone ~4.7 s after start). A 2 s watch asks a stopped player to play again whenever it should be playing (on screen, tab visible, not paused by the viewer: `userPausedRef`), since browsers pause muted trailers on their own; after 3 stopped checks it sets `blocked` (autoplay is blocked: an iPhone in Low Power Mode, strict settings) and the play control pulses in gold for the one tap that works. The hero holds only the greeting and "Now showing" over the trailer. Start and Join: below `md` one floating card with a tab each (`QuickActions`: both panels one height, so switching moves nothing) overlapping the hero's bottom edge (`-mt-12`, "Now showing" raised to `bottom-16` to clear it, hero `min-h-[22rem]`); from `md` a section of their own under the hero with the two full cards. At every width the trailer is at nearly full strength, 90% under a light `ink/10` veil, shaded only at the top (header, greeting), the bottom (fading into the page) and, from `lg`, a light left-hand gradient behind the greeting. Below `lg` it is the whole hero with a `hqdefault` still; "Now showing" is one fixed-height row (title, play/pause, sound, Watch) in the space the hero reserves. The player is created ~1 s after load, pauses when the tab is hidden or the hero scrolls away, skips a video that errors and gives up after three errors in a row. The backdrop must stay inside its `relative isolate` wrapper (`inset-0`, never overflowing below): a stacking context there paints over the non-positioned sections that follow.
- **No layout shift:** anything that arrives after first paint must not move what is already on screen. The home greeting depends on the session, which the static HTML can't know (the refresh cookie is HttpOnly on the API origin), so an inline script in `layout.tsx` (`AUTH_HINT`) reads the display name `auth-context` saved in `localStorage` (`wp.name`) and sets `data-auth` and `--wp-name` on `<html>` before paint; while the session loads, `HomeGreeting` renders both versions and CSS (`.auth-in`/`.auth-out`, `.wp-name`) shows the right one. Late content gets reserved space ("Now showing": the hero's `lg:min-h-64` row and its phone bottom padding). Measure with Lighthouse on a production build before and after touching the home page.
- **Performance:** `app/page.tsx` is a server component; only `components/home/*` and the nav hydrate. `ResourceHints` preconnects to the API and `i.ytimg.com`. `AddContentFlow` is loaded with `next/dynamic` and rendered only while open, and `HostedPlayer` imports `hls.js` on demand for `.m3u8` only; keep heavy, rarely-used code out of a page's first load the same way. Starting a party from anywhere (the home card, the trending row, Discover) goes through `useStartParty`, which sends a visitor to sign in first.
- **Primitives:** `components/ui.tsx` (`Button` with variants primary (off-white)/light (same)/secondary/ghost/subtle/danger and sizes sm/md/lg, `IconButton`, `Input` (accepts a `ref`), `PasswordInput` (eye toggle; use it for every password field), `Field`, `Eyebrow`, `Banner` info/error/success, `LiveDot`, `Logo`, `Avatar` (muted greys, cream initials), `Accent`), `AuthShell` for sign-in pages, `Sheet` (bottom sheet on a phone; `onBack` for a step inside it; portalled to `<body>`, because a transformed ancestor such as `animate-rise` would trap anything `fixed`, and sized to the visual viewport so it sits above the on-screen keyboard), and `Poster` for any video artwork. `Poster` scales YouTube's 4:3 `hqdefault` thumbnails by 4/3 to crop the built-in letterbox bars, so use it instead of a bare `<img>`. `AddContentFlow.tsx` also exports `LinkForm` and `useSources`, which Discover reuses.
- **Room layout:** below `lg` the room is an app screen (`h-dvh`, no page scroll): a compact header (back, title, "N watching · CODE", the Invite pill, `HostMenu`, which also holds "Change what's playing" on a phone), the player inset with rounded corners, `SyncStatus`, then the Chat / Up next / People panel (a segmented control) filling the rest with the message box at the bottom. Reactions live in the chat bar there (`ChatPanel` `onReact`), and the guest prompt sits in the People tab. `land:` puts player and panel side by side. From `lg` it is two columns: the wordmark in the header, stage, then `ReactionBar` and `SyncStatus` (with avatars) on the left, the sticky panel on the right. The player's controls lay themselves out with container queries (`@container` on `.stage`: ±10 s buttons and picture-in-picture from `@md`, the volume slider and desktop sizes from `@xl`). `InviteBar.tsx` exports `InviteButton` (the off-white Invite pill) and `RoomCodeChip` (code + copy, `lg` up).

### Other conventions
- REST controllers are mapped under both `/api/v1/...` and `/api/...`.
- Errors: throw `common.ApiException`; `GlobalExceptionHandler` shapes `ErrorResponse`.
- Rate limits: REST in `ratelimit/RateLimitFilter` (exact-path match on POST), realtime inside the services; all policies live in `RateLimits` and are counted in Redis, so they hold across instances.
- Config lives in `application.properties` bound to `config/AppProperties` (`app.*`, a record, so a new field needs a property *and* an update to the `AppProperties` constructed in `JwtServiceTest`). Env overrides include `ROOM_MAX_MEMBERS`, `ROOM_HOST_GRACE`, `ROOM_EMPTY_GRACE`, `ROOM_MAX_QUEUE`.
- **New-message notice** (`app/room/[code]/page.tsx`): a message from someone else while the chat is not in view shows a card (portalled into `document.fullscreenElement` when there is one, since only that element is drawn in fullscreen), a count on the Chat tab, and `(N)` in the page title. "In view" means Chat tab open, page visible *and* not fullscreen. Your own messages never count as unread. Desktop notifications are opt-in via the bell (`wp.notify` in localStorage) and fire only while the tab is hidden.
- The reaction allowlist exists twice, `ChatService.REACTIONS` and `REACTIONS` in `frontend/src/lib/types.ts`, and the two must match byte for byte (❤️ is U+2764 U+FE0F).
- Frontend entry points: `app/room/[code]/page.tsx` + `hooks/useRoom.ts` own a room session; `lib/connection.ts` is the STOMP session; `components/AddContentFlow.tsx` is the "+" picker, reused both for change-video and add-to-queue (and, as a page, by `app/discover`); `PlayerSurface` picks the player, draws the controls, the reaction overlay and the guest hint, passes `onEnded` to the players and shows chat-only mode for DRM rooms.
