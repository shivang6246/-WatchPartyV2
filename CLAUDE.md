# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

WatchParty: synced watch parties in any browser (phones included) for YouTube, direct MP4/WebM/HLS and Vimeo. One Spring Boot backend serves both the Next.js web client in `frontend/` and a separate Chrome extension (not in this repo) that handles DRM platforms on desktop. `README.md` is the design doc — read it before changing sync, auth or data-model behavior.

- `backend/` — Spring Boot 3.5, Java 21, Maven (no wrapper; use a local `mvn`). Supabase (Postgres, via JPA/Hibernate + Flyway) for durable data, Redis for hot state.
- `frontend/` — Next.js 16, React 19, Tailwind 4, `@stomp/stompjs`. **Read `frontend/AGENTS.md`**: this Next.js version has breaking changes; consult `frontend/node_modules/next/dist/docs/` before writing Next code. That file is regenerated by `next dev`.
- `ops/` — `Caddyfile` (TLS proxy, `proxy` profile), `prometheus/` and `grafana/` (the `observability` profile; the dashboard JSON is in `ops/grafana/dashboards/`).

## Commands

Full stack (needs `.env` from `.env.example`: `DATABASE_URL`/`DATABASE_USER`/`DATABASE_PASSWORD`, `REDIS_PASSWORD`, `JWT_SECRET`; `YOUTUBE_API_KEY` optional):

```bash
docker compose up -d --build                       # Supabase via DATABASE_URL
docker compose --profile local-db up -d --build    # bundled postgres:16 instead
SITE_ADDRESS=your.domain docker compose --profile proxy up -d   # Caddy/TLS
docker compose --profile observability up -d       # Prometheus + Grafana on :3001 (needs GRAFANA_PASSWORD)
```

Web on http://localhost:3000, API + Swagger at http://localhost:8080/swagger-ui.html. Postgres and Redis publish no ports.

Running the backend outside Docker (IDE or `mvn spring-boot:run`) reads `backend/.env.local` (gitignored; template in `backend/.env.local.example`) via `spring.config.import`, and needs a reachable Redis (`REDIS_HOST`, `REDIS_PASSWORD`). It deliberately does *not* read the root `.env`: that sets `REDIS_PASSWORD` for the compose Redis, which would break a passwordless local Redis. There are no defaults for the database or `JWT_SECRET`: both blank means startup fails, by design.

### Where secrets live
Two gitignored files, by who reads them, plus the host's secret store in production. A value used in both places has to be set in both.

| | reader | holds |
| --- | --- | --- |
| `backend/.env.local` | Spring, for a run outside Docker | `DATABASE_*`, `JWT_SECRET`, `REDIS_PASSWORD`, `YOUTUBE_API_KEY`, `GOOGLE_CLIENT_*`, `SMTP_*`/`MAIL_FROM`/`WEB_BASE_URL` |
| root `.env` | Docker Compose only | the same, plus `POSTGRES_PASSWORD`, `GRAFANA_PASSWORD`, `SITE_ADDRESS`, `NEXT_PUBLIC_*` |
| host secret store | production | everything above; never deploy a `.env` file |

- **Never put a literal secret in `application.properties`** (it is committed): always `${VAR}` or `${VAR:}`. Same for `docker-compose.yml`, Dockerfiles, source and tests.
- **`NEXT_PUBLIC_*` is public** — it is compiled into the bundle every visitor downloads, so it holds only the API/WS URLs and feature flags. This is why the YouTube key is proxied server-side (see Catalog).
- `.gitignore` covers `.env` and `.env.local` at any depth; the `*.example` templates are committed and must stay free of real values.
- Production uses its own `JWT_SECRET` and database, never the local ones. Rotating `JWT_SECRET` signs everyone out (tokens carry a `kid` header, so a rotation can be staged).

Backend (from `backend/`):

```bash
mvn spring-boot:run
mvn test
mvn test -Dtest=RoomStateTest              # single class
mvn test -Dtest=RoomStateTest#methodName   # single method
mvn clean package -DskipTests

Unit tests cover pure logic only (projection, video sources, JWT, queue rules, host succession); anything touching Redis/Postgres/STOMP is covered by the smoke script instead. Any Spring property can be overridden on the command line (`--app.room.host-grace=6s`), which is how to exercise the watchdog quickly.

```bash

npm run typecheck      # tsc --noEmit
npm run lint           # `next lint` — may not exist in Next 16

It opens 4 sockets, and `WS_CONNECT` allows 5 per minute per IP, so back-to-back runs within a minute fail at connect. Host *failover* is not in the smoke run (it waits on the grace period). ## Architecture

### Two stores, strict split
Postgres on Supabase (eight tables: `app_user`, `refresh_token`, `email_verification`, `pending_registration`, `room`, `room_member`, `chat_message`, `playback_event`) is durable truth. Redis holds live playback state, presence, watchdog deadlines, cross-instance fan-out, rate-limit counters and the YouTube search cache. `sync/StateSnapshotJob` writes Redis state back to Postgres every 30 s, updates the active-room gauge, asks the watchdog to audit each room and expires rooms. `sync/RetentionJob` purges chat/playback history 30 days after close and deletes expired refresh tokens, verification links and finished/abandoned sign-ups (Postgres has no TTL index).

- **Schema changes are new Flyway files** in `backend/src/main/resources/db/migration` (`V2__...sql` and so on). Never edit an applied migration: Flyway checksums it and refuses to start. Hibernate runs `ddl-auto=validate`, so an entity that drifts from the SQL fails at boot. Tables live in the `watchparty` schema, not `public` (Supabase exposes `public` via its REST API with the anon key). Every table has RLS enabled with no policies, so new tables need `alter table ... enable row level security` too. Don't `ALTER` `flyway_schema_history` inside a migration: Flyway holds a lock on it and the migration deadlocks.
- **Every write to an existing room goes through `RoomService.mutate`** (or `tx.execute` with `rooms.findByIdForUpdate`): a short transaction that takes the row lock (`SELECT ... FOR UPDATE`), applies the change to the fresh copy, and commits. Host edits, queue advances from any member and the snapshot sweep all write that row; the lock serialises them so none undoes another. Don't `rooms.save()` a room loaded earlier in the request; `save` of a new room is only in `create`. `@Transactional` on a method called from the same class does nothing (proxy), which is why `RoomService` uses a `TransactionTemplate`.
- Entities extend `common/AssignedIdEntity`: the UUID is assigned at construction (ids are needed before save), and `Persistable.isNew` makes the first save a plain INSERT. That's also what lets the `(room_id, user_id)` unique constraint catch two racing joins (`join` catches `DataIntegrityViolationException` and returns the winner's row).
- `spring.jpa.open-in-view=false`: nothing lazy-loads outside a transaction, and there are no JPA associations; rows reference each other by id columns.
- No joins needed for display: denormalize display data (author name on chat messages and queue items, video title/thumbnail on the room).

### Realtime path
STOMP over `/ws` (`config/WebSocketConfig`). Client sends to `/app/room/{roomId}/{playback|chat|reaction|typing|heartbeat|resync}` and `/app/session/time`; server broadcasts on `/topic/room/{roomId}/{playback|chat|members|activity}` and per-user `/user/queue/{errors,time}`. Handlers live in `sync/RealtimeController`.

- `chat` carries only stored `ChatMessageView`s: the Chrome extension renders that topic, so don't put other event shapes on it. Ephemeral events (reactions, typing) go on `activity`.
- `members` carries typed events (`roster`, `health`, `left`, `room`, `closed`, `host`, `host-away`, `host-back`, `host-lost`, `queue`); `MemberEvent` in `frontend/src/lib/types.ts` mirrors them.
- **Presence is live, and the Redis presence set is its only source.** `RoomStateService.heartbeat` returns true when a member *becomes* present, and that transition broadcasts the roster: on STOMP CONNECT (`StompAuthInterceptor`) and on a heartbeat after a gap (`RealtimeController.heartbeat`, which also heals a "left" sent when one of two tabs closed). A disconnect publishes `left`. Members who time out without one are pruned only by `expirePresence` in the snapshot sweep's `audit`, which publishes `left` for each; `presentMembers` filters by score and never prunes, so nothing else can swallow a departure. The client diffs rosters in `useRoom` into `presence` (joined/left) lines in the chat timeline. A leave followed by a rejoin within 15 s (a reload) shows nothing.
- Sending a SEND/SUBSCRIBE to another room's destination is fatal to the session by design (interceptor throws → ERROR frame).

All broadcasts go through `sync/RoomEventPublisher`, never `SimpMessagingTemplate` directly. It publishes an `Envelope` to the single Redis channel `wp:room-events`; `RoomEventSubscriber` on every instance (including the sender) calls `deliverLocally`. Three modes: `publish` (room topic), `sendToMember` (a member's `/user/queue/errors` on whatever instance holds them) and `disconnectMember` (same, then closes their sockets). `sendError` is local-instance only, so use it only for replying to the frame being handled. Member notices carry `roomId`, because a user destination reaches that account's tabs in other rooms too, and the client filters on it.

`security/SessionRegistry` maps raw WebSocket sessions to member ids (registered by a handler decorator in `WebSocketConfig`, bound at CONNECT in `StompAuthInterceptor`). That's what lets a kick actually close a socket, with close code 4001 (`SessionRegistry.REMOVED`), which the client treats as "don't reconnect".

### Room watchdog (`sync/RoomWatchdog`)
There are two Redis sorted sets of deadlines, `wp:watch:host-away` and `wp:watch:room-empty`, scored by due time. A 5 s sweep claims due entries with `ZREM`, so exactly one instance acts on each. Every deadline is re-checked against live presence when it falls due.
- Signals come from: STOMP CONNECT (`onMemberConnected`: marks presence, cancels both), `SessionLifecycleListener` on disconnect and REST leave (`onMemberGone`), and `audit()` from the snapshot sweep, which catches members who aged out without a disconnect.
- Host away: `app.room.host-grace` (45 s), then `pickSuccessor` picks the earliest-joined, present, registered, non-removed member → `RoomService.transferHost(..., "failover")`. With only guests left, the room is unlocked and gets a `host-lost` event.
- Empty: `app.room.empty-grace` (10 m), then `RoomService.closeRoom(room, "empty")`. All closes (host / empty / expired) go through `closeRoom`.

### Sync engine (server `sync/`, client `frontend/src/lib/{clock,sync,player}.ts`)
- Room state is a position anchored to a server timestamp plus speed; clients compute `position + (now - anchor) * speed` against their own corrected clock. Never broadcast a live position.
- `RoomStateService` applies each event in a Redis Lua script that writes state and assigns a monotonic per-room sequence atomically. Clients drop any event whose sequence isn't greater than the last applied. Keep ordering inside that script.
- A new video (host change or queue advance) goes through `RoomStateService.resetPlayback`, which continues the sequence from `max(live, snapshot) + 1`. Don't use `clear` + `hydrate` for this: `hydrate` seeds the sequence from the up-to-30 s-old snapshot, and clients would drop the reset.
- **Playback is host-only**: `Room.locked` is always `true` while the room has a host, so `PlaybackService` refuses play/pause/seek from anyone else (`room_locked`, with the authoritative state sent back). Hosts cannot unlock it: `PATCH {locked:false}` is 403 `host_only_playback`, and `HostMenu` has no such option. The one exception is the watchdog: a room whose host is lost with only guests left is unlocked so it can't freeze, and `RoomWatchdog.onMemberConnected` re-locks it the moment a host connects (which also re-locks rooms unlocked before this rule). Queue advance on `ended` is a REST call and ignores the lock.
- Client positions are never authoritative: seeks are requests, validated against media duration and re-stamped with the server clock. Heartbeat positions are telemetry only (they drive the host's "N members behind" and the drift histogram).
- In a paused room always `pause()` *before* `seek()`, and `SyncEngine.tick` re-pauses any player whose `isPlaying()` is true. YouTube's `seekTo` resumes a player that isn't already paused; seek-then-pause leaves the video running while the engine keeps seeking it back (it plays in stutters instead of freezing).
- The reverse holds too: `tick` calls `play()` on a player that stopped while the room plays (a click on the YouTube iframe, an autoplay block, a backgrounded tab). It doesn't do this in the last 1.5 s, where a stopped player has simply finished and `play()` would restart it from 0. After 3 stalled ticks `diagnostics.blocked` is set, and `PlayerSurface` shows a "tap to join in" button that calls `SyncEngine.userStart()` inside the click (only a user gesture clears an autoplay block).
- A seek intent carries the room's *current* `playing` (`playingRef`), never `true`, so scrubbing never starts or stops the room.
- `PlayerSurface` covers embedded players with a transparent button, so a click on the picture toggles the *room*; the player's own click-to-pause would only pause that one screen. The scrub bar commits on pointer-up, touch-end, key-up and blur, and holds the target for 1.5 s so it doesn't snap back during the round trip. Space/K toggle and ←/→ skip 10 s (ignored while typing). The duration is polled every tick until the player reports one, because YouTube often has none at `onReady`, and without it the bar stays disabled.
- Clock sync: 5 probes on connect and every 30 s, offset from the lowest-RTT probe.
- **Local-only player controls** (never sent to the room): volume/mute, quality and fullscreen live on `PlayerHandle` (`setVolume`, `setMuted`, `getQualities`/`setQuality`, optional `requestNativeFullscreen`). `PlayerSurface` polls the handle every 250 ms and shows the quality menu only when `getQualities()` has more than one entry. `.m3u8` goes through **hls.js whenever `Hls.isSupported()`** (imported on demand, so other rooms never download it), native only as the fallback (iOS Safari): Chrome answers `"maybe"` to `canPlayType` for HLS and then plays it with no quality ladder. YouTube returns no qualities on purpose (its quality API is deprecated and ignored). `HostedPlayer` re-announces its handle when the ladder arrives, which is what makes the menu appear.
- **Fullscreen** takes the whole `.stage` section (screen + transport), not the bare player, so sync readout and controls come along; the layout is in `.stage:fullscreen` in `globals.css`. iOS only allows fullscreen on the `<video>` itself (`requestNativeFullscreen`). Shortcuts: F fullscreen, M mute.
- Drift ladder: <250 ms nothing; 250 ms–2 s rate 0.97/1.03; >2 s hard seek; >30 s resync (the client also sends `/resync`). YouTube can't do fine rates (`PlayerHandle.fineRateSupported = false`), so it uses 0.75/1.25 up to 2.5 s and only seeks beyond that, since a YouTube seek costs seconds of buffering. `SyncEngine.drainCorrections()` counts each tier, and those counts ride on the next heartbeat for metrics.
- **A seek on a playing room aims ahead** (`SyncEngine.seekPlaying`): at the projection plus a lead, because the room keeps moving while the player loads. Seeking to "now" lands the player behind by its load time, which triggers another seek, forever (endless buffering at a steady few seconds of drift). The lead starts at 900 ms for YouTube and 150 ms for a video element, and is learned from where each seek lands (damped, capped at 6 s). `hardApply` only plays or pauses a player that is already within `ignoreMs`, so play/pause events and resyncs don't seek in-sync players.
- The ladder holds off when its measurement can't be trusted, because on YouTube every seek re-buffers. **While the player is buffering** (`SyncEngine.setBuffering`, fed from `useRoom.setBuffering`) nothing corrects for up to 8 s: seeking a player that is refilling throws the buffer away and turns one stall into a loop. After it refills there is a 700 ms settle. **A tick more than 1.8 s after the previous one** (the page's thread was blocked) is skipped, since the player's reported position is stale then.
- Never resize the player as a side effect of UI: YouTube switches quality on a resize and re-buffers. That is why the viewport has no `interactiveWidget: "resizes-content"` (the keyboard would reflow the room) and why the landscape player is sized in `svh`. Keep chat rendering cheap too (`ChatPanel`'s list is memoised, timestamps use one shared `Intl.DateTimeFormat`): on Android the YouTube iframe often shares the page's main thread.

### Queue
`Room.queue` is a `jsonb` column holding only *upcoming* `QueueItem`s. They're serialized field by field (`@JsonAutoDetect`), and equality is by `itemId` so Hibernate can tell an unchanged queue. The current video stays in the room's `video*` fields, identified by `currentItemId`. Always assign a *new* list (`setQueue`), never mutate in place. Every queue write happens under the row lock. Reorder must name every current item exactly once, else 409 `queue_changed`. An advance checks `currentItemId` under the lock, which makes N members all reporting "ended" at once advance the queue only once. Any member may report `ended`, but the server only accepts it if its own projection is within 5 s of its own known duration (the reporter's duration is never trusted). `skip` and all edits are host-only via `requireQueueControl`. Max length is `app.room.max-queue`.

### Auth model (`auth/`, `security/`)
A token proves identity only; every room operation loads the caller's `room_member` row and checks its `MemberRole`. Credentials: access JWT (15 min, memory), rotating refresh token with reuse detection (HttpOnly cookie `wp_refresh`, hashed at rest, TTL index), guest token (one room, ≤24 h), and a WebSocket ticket (30 s, single use, from `POST /api/v1/ws-ticket`, sent as the STOMP `ticket` connect header and checked by `StompAuthInterceptor`) — never put the JWT in the WS URL. The room code alone is enough to join: `GET /rooms/{code}/preview` is public, and `POST /auth/guest` takes `roomCode` *or* `inviteToken`, then `join` needs no invite. The invite link still works. Code guessing is slowed by the per-IP `ROOM_LOOKUP` (preview) and `GUEST_ISSUE` limits; a guest pass stays scoped to its one room. Hosts must be registered users; only the host's `RoomView` carries `inviteToken` (the client refetches after becoming host). A guest who registers mid-room has their member row rebound, not duplicated. Removed members are refused at ticket, join, CONNECT and every frame; muted members can't chat, react or send typing, and the host can't be muted or removed.

**Email verification (`auth/EmailVerification*`, `auth/Mailer`, `auth/MailConfig`):** one email carries a six-digit code *and* a link, both on the same row (256-bit token and the code, each SHA-256 hashed at rest, `app.verification.ttl` 24 h). They gate exactly one thing — `RoomService.create`. Guests never need an account, so an unverified user can still join, watch, chat and react; only hosting is refused (403 `email_unverified`). Issuing deletes the account's earlier unused rows, so an old email stops working. Google accounts are verified on creation.
- `POST /auth/verify` (link) is public: the token is the proof, and mail is often opened on a device that is not signed in. `POST /auth/verify/code` and `/auth/verify/resend` need the session, because six digits is only meaningful against one account.
- The code row counts wrong tries and dies after `MAX_CODE_ATTEMPTS` (6); that, not the hash, is what makes guessing pointless. The message says how many are left, then tells them to ask for a new code.
- **Where verification is enforced, `register` creates no account.** The sign-up (password already hashed, plus any guest pass so the seat is kept) waits in `pending_registration` and `register` answers 202 `{pending, email}` with no session. `POST /auth/register/confirm` takes `{email, code}` or `{token}`, creates the account already verified and signs it in; `/auth/register/resend {email}` re-sends. Registering the same address again replaces the waiting row. The client goes `/register` → `/verify?email=…` (code form); the email's link is `/verify?signup=…`. With verification not enforced, `register` signs in straight away as before (the smoke run relies on this).
- The older per-account path (`/auth/verify`, `/verify/code`, `/verify/resend`, link `/verify?token=`) remains for accounts created unverified before this, or on a stack that doesn't enforce verification.
- **Enforcement follows the mail setup**: `EmailVerificationService.required()` is true when `spring.mail.host` is non-blank, and `app.verification.required` overrides either way. With no SMTP the mail is logged instead, so a dev machine (and the smoke run) can host freely. Pick the `Mailer` on a *non-blank* host, not on the property merely being set: `${SMTP_HOST:}` leaves an empty string behind.
- `management.health.mail.enabled=false` — otherwise the health endpoint dials SMTP and reports the whole app down when no host is set.

**Client token handling:**
- `useRoom`'s `tokenRef` holds only a *guest pass*. Signed-in users pass no token, so `apiFetch` sends the current in-memory access token and refreshes it on a 401.
- Never pin an access token in a ref or closure: it expires after 15 min, and `apiFetch` skips the refresh whenever a token is passed explicitly.
- `RoomConnection.beforeConnect` must never throw (stompjs would surface it as an uncaught error). Ticket failures with 401/403 call `onAuthFailed`, which clears a dead guest pass and re-enters the room; other failures retry after 3 s. A 401/403 from `join` also falls back to the name screen. To test expiry quickly, start the backend with `--app.jwt.access-ttl=15s`.

### Catalog (`catalog/`)
youtube.com cannot be iframed, so "YouTube in the app" means the backend proxies the Data API (`/api/v1/catalog/youtube/{search,trending}`, cached in Redis ~10 min because searches cost 100 quota units) and the client renders the results, embedding only the IFrame player. The API key stays server-side. With no key, `/catalog/sources` reports `browsable: false` and `/catalog/resolve` uses keyless oEmbed; that must keep working.

### Observability
Every meter is defined in `metrics/WatchPartyMetrics` (keep tag values bounded; never tag with ids or user input). Exposed at `/actuator/prometheus`, which is `permitAll` in `SecurityConfig` and kept private by Caddy (`/actuator/*` → 404) and the loopback-only port. Prometheus names: `watchparty_rooms_active`, `watchparty_ws_sessions`, `watchparty_redis_apply_seconds`, `watchparty_sync_drift_milliseconds`, `watchparty_sync_corrections_total{tier}`, `watchparty_playback_events_total{action,result}`, plus counters for chat, reactions, failovers, closes, kicks and queue advances. If you rename a meter, update `ops/grafana/dashboards/watchparty-overview.json`. In Docker, logs are ECS JSON (`LOGGING_STRUCTURED_FORMAT_CONSOLE`, set via `LOG_FORMAT`); use SLF4J `addKeyValue` for fields you want queryable (see `PlaybackService.recordCorrections`).

### Design system (frontend)
Clean, dark and mobile-first: near-black surfaces, off-white type, one electric-cobalt accent, and the halo (a ring of white light) as the only ornament. Build for a 390px phone first and widen from there.
- **Tokens:** all colours live in `@theme` in `src/app/globals.css` (`ink`, `stage`, `panel`/`panel-2`/`panel-3`, `line`/`line-strong`, `cream` (the off-white type colour), `muted`, `faint`, `cobalt`/`cobalt-bright` (hover)/`cobalt-soft` (accent text)/`cobalt-deep`, `ember` for danger/live, `sage` for present/ok). Use those utilities, never raw Tailwind palettes (`zinc-*`, `rose-*`…). Put white text on `bg-cobalt`, never `text-ink`.
- **Fonts:** self-hosted with `next/font/google` in `layout.tsx`: Geist → `font-sans` for everything, including headlines (semibold, tight tracking); Geist Mono → `font-mono` for codes and timecodes (not preloaded); Instrument Serif **italic only** → `font-serif`, for an accent word or two via `Accent` in `ui.tsx`. Never use `font-serif` without `italic`: no upright file is loaded.
- **CSS helpers:** `.spotlight` (static cobalt light from the top, per page), `.halo` (the ring; absolutely positioned, size it with a width; `.halo-dim` for an "off" one; its glint only animates on a desktop with motion allowed), `.panel`, `.ticket` (dashed mono room code), `.thin-scrollbar`, `.no-scrollbar`. `body` has `overflow-x: clip` because glows bleed on purpose; don't switch it to `hidden` (it would break the sticky side panel).
- **Mobile rules:** inputs are 16px below `sm` (`text-base sm:text-sm`), or iOS zooms on focus. Tap targets are at least 40px. Use `dvh`, not `vh`, for full-height layouts. No `backdrop-blur`, blend modes or animated filters on anything big (they are what makes a phone stutter); the one large blur, the player's ambilight, is `lg:` only. `land:` (a custom variant: landscape, under 560px tall, under `lg`) is a phone on its side.
- **Performance:** `app/page.tsx` is a server component; only `components/home/*` hydrate. `AddContentFlow` is loaded with `next/dynamic` and rendered only while open, and `HostedPlayer` imports `hls.js` on demand for `.m3u8` only; keep heavy, rarely-used code out of a page's first load the same way.
- **Primitives:** `components/ui.tsx` (`Button` with variants primary (cobalt)/light (white)/secondary/ghost/subtle/danger and sizes sm/md/lg, `IconButton`, `Input` (accepts a `ref`), `PasswordInput` (eye toggle; use it for every password field), `Field`, `Eyebrow`, `Banner` info/error/success, `LiveDot`, `Logo`, `Avatar`, `Accent`), `AuthShell` for sign-in pages, `Sheet` (bottom sheet on a phone; `onBack` for a step inside it), and `Poster` for any video artwork. `Poster` scales YouTube's 4:3 `hqdefault` thumbnails by 4/3 to crop the built-in letterbox bars, so use it instead of a bare `<img>`.
- **Room layout:** below `lg` the room is an app screen (`h-dvh`, no page scroll): a compact header (back, title, "N watching · CODE", share icon, host `+` and `HostMenu`), the player edge to edge, then the Chat / Up next / People panel filling the rest with the message box at the bottom. Reactions live in the chat bar there (`ChatPanel` `onReact`), and the guest prompt sits in the People tab. `land:` puts player and panel side by side. From `lg` it is two columns: stage, `ReactionBar` and `WatchingSummary` on the left, the sticky panel on the right. The player's transport lays itself out with a container query (`@container` on `.stage`, `@xl:` = one row); on a narrow stage it is a full-width scrub bar over one row of buttons. `InviteBar.tsx` exports `InviteButton` (an icon on a phone, code + Invite from `sm`).

### Other conventions
- REST controllers are mapped under both `/api/v1/...` and `/api/...`.
- Errors: throw `common.ApiException`; `GlobalExceptionHandler` shapes `ErrorResponse`.
- Rate limits: REST in `ratelimit/RateLimitFilter` (exact-path match on POST), realtime inside the services; all policies live in `RateLimits` and are counted in Redis, so they hold across instances.
- Config lives in `application.properties` bound to `config/AppProperties` (`app.*`, a record, so a new field needs a property *and* an update to the `AppProperties` constructed in `JwtServiceTest`). Env overrides include `ROOM_MAX_MEMBERS`, `ROOM_HOST_GRACE`, `ROOM_EMPTY_GRACE`, `ROOM_MAX_QUEUE`.
- **New-message notice** (`app/room/[code]/page.tsx`): a message from someone else while the chat is not in view shows a card (portalled into `document.fullscreenElement` when there is one, since only that element is drawn in fullscreen), a count on the Chat tab, and `(N)` in the page title. "In view" means Chat tab open, page visible *and* not fullscreen. Your own messages never count as unread. Desktop notifications are opt-in via the bell (`wp.notify` in localStorage) and fire only while the tab is hidden.
- The reaction allowlist exists twice, `ChatService.REACTIONS` and `REACTIONS` in `frontend/src/lib/types.ts`, and the two must match byte for byte (❤️ is U+2764 U+FE0F).
- Frontend entry points: `app/room/[code]/page.tsx` + `hooks/useRoom.ts` own a room session; `lib/connection.ts` is the STOMP session; `components/AddContentFlow.tsx` is the "+" picker, reused both for change-video and add-to-queue; `PlayerSurface` picks the player, draws the reaction overlay, passes `onEnded` to the players and shows chat-only mode for DRM rooms.

## Out of scope for v1
Netflix/Prime/Disney+ playback (the extension's job), uploads/transcoding, voice/video chat, native apps.
